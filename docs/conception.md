# Mon Dressing — conception

Les règles et les choix techniques de l'app, écran par écran. C'est la référence du code : les
commentaires citent ses sections (« docs/conception.md §5 »), dont les numéros ne changent pas.
Les points marqués **[À mesurer]** se vérifient sur la tablette elle-même, derrière le miroir.

Pour installer le projet, commence plutôt par le [README](../README.md).

## 1. Le produit en une phrase
Le matin, on passe devant le miroir : il voit que quelqu'un est là, propose une tenue adaptée à la
météo, composée avec ses propres vêtements ; on la change d'un geste du bras, on la valide d'un pouce
levé, on la refuse d'un poing fermé.

« Il voit que quelqu'un est là » veut dire qu'il **détecte une présence** et se réveille. Il n'y a pas
de reconnaissance faciale : l'app n'a qu'un compte.

## 2. Matériel de référence
| Élément | Détail | Conséquence pour le code |
|---|---|---|
| Tablette | Android, environ 12 pouces, écran 2560×1600, montée en **portrait** | Viewport de référence 800×1280 à DPR 2 (celui des tests e2e) **[À mesurer]** sur la tablette choisie : `innerWidth`, `innerHeight` et `devicePixelRatio` en portrait, qui dépendent aussi de la taille d'affichage réglée dans Android |
| Support | Fixation murale, tablette branchée en permanence | Pas de gestion de batterie, écran toujours allumé |
| Miroir | Plaque acrylique sans tain (environ 3 mm) posée devant l'écran | **Le tactile ne marche pas.** Seul ce qui est clair sur fond noir se voit |
| Caméra | Caméra frontale de la tablette (1080p suffit, l'autofocus n'est pas nécessaire), un trou dans le miroir devant elle | **C'est la commande du miroir** : les gestes des bras, faits à 1–2 m, lumière de chambre, analysés sur la tablette (§5) |
| Commande | **Pas de manette** : le miroir se commande avec les mouvements des bras devant la caméra (§5) | Un clavier (PC, tests) reste en secours avec les touches de PC par défaut ; aucune télécommande à appairer ni à recharger |

Le code ne suppose aucune manette ; l'écran « Test des touches » ne sert qu'à un clavier de secours aux
touches inhabituelles (§5). Le matériel en détail : [materiel.md](materiel.md).

## 3. Données
Tables Postgres (noms en anglais, RLS activé partout). Chaque table a une colonne `owner uuid not null default auth.uid() references auth.users`, et ses policies sont `owner = auth.uid()`. `outfit_history` est unique sur (`owner`, `date`), et `profile` a `owner` pour clé primaire. Les fichiers de Storage sont rangés sous `<user_id>/…`, avec la même règle (AGENTS.md). Le rôle `authenticated` (le compte connecté) reçoit `select`, `insert`, `update` et `delete` sur ces tables : un projet Supabase récent n'expose plus d'office les tables à la Data API. Tout le schéma est dans `supabase/schema.sql`.
- **items** (vêtements) :
  - `name` : nom ;
  - `category` : `haut` | `bas` | `robe` | `veste` | `chaussures` | `accessoire` ;
  - `color` : couleur principale, `#RRGGBB` ;
  - `warmth` : chaleur, de 1 à 3 ;
  - `styles` : un ou plusieurs styles parmi `decontracte`, `habille`, `sport`. Une liste plutôt qu'une valeur unique : une pièce sert souvent à plusieurs styles, et le format db.json (§3.1) stocke déjà une liste ;
  - `rain_ok` : ok pluie (booléen) ;
  - `dirty` : au sale (booléen) ;
  - `photo_path` : photo d'origine (pour une pièce assemblée : la photo portée, fond vert compris, en JPEG) ;
  - `cutout_path` : image détourée à fond transparent dans le bucket privé `items` (pour une pièce assemblée : la photo portée détourée, en WebP ; plusieurs pièces peuvent partager la même photo) ;
  - `assembly` (jsonb, facultatif) : repères d'assemblage de la photo portée (§7) ;
  - `legacy_id` : identifiant d'origine (db.json ou paquet d'assemblage), unique par compte, pour rejouer un import sans doublon ;
  - `created_at` : date d'ajout.
- **outfit_history** (historique) : une entrée par jour, avec `date` (unique), `item_ids` (les pièces portées) et `title` (titre de la tenue, facultatif).
- **outfit_plans** (« Préparer demain ») : une tenue prévue par date, avec `date` (unique par `owner`), `item_ids` et `confirmed` (vrai une fois gardée pour demain).
- **refusals** (refus) : associations de pièces refusées, à ne plus reproposer ensemble. `item_ids` est trié et unique, `created_at` en plus. Granularité : voir §6.
- **profile** :
  - `photo_path` : inutilisée (pas d'essayage virtuel, §7) ;
  - ville : `city`, `lat`, `lon`, et `timezone` (IANA, `Europe/Paris` par défaut, avec Paris comme ville par défaut : à changer dans Réglages) ;
  - `key_map` (touches d'un clavier de secours → actions, §5 ; vide : touches de PC) ; `key_test_requested` : inutilisée (le téléphone ne demande plus de test des touches) ;
  - réglages des gestes (`gestures_enabled`, `gesture_sensitivity`) : pas encore utilisés, les seuils sont les constantes du §5 ;
  - `tryon_cap_eur` : inutilisé (pas d'essayage, §7).
- **spend_ledger** : suivi des dépenses d'API (fiche Claude, détourage Bria). **tryon_cache** : inutilisée (pas d'essayage, §7).

### 3.1 Import d'un dossier `Dressing/` (zip simple, format db.json)
Format hérité d'un premier prototype, gardé pour le mode simple ([photos-simple.md](photos-simple.md)) : il faut une correspondance avec le nouveau modèle. Les données sont dans un dossier `Dressing/` qui contient `db.json` et `photos/`. Les images sont des fichiers à part. Format d'import accepté :
- un **zip de ce dossier**, pour les fiches et les images ;
- ou **`db.json` seul**, pour les fiches sans images.

`db.json` est cherché à la racine du zip ou dans un dossier (le moins profond l'emporte), les images dans le `photos/` qui est à côté de lui, sinon dans n'importe quel `photos/` du zip (jamais `trash/` ni `drafts/`). Le zip est ouvert dans le navigateur. Chaque image est envoyée directement dans Storage, puis `db.json` et les chemins sont envoyés au serveur. Aucune requête vers Vercel ne dépasse 4 Mo, car Vercel refuse les corps de plus de 4,5 Mo.

| `db.json` | Nouveau modèle |
|---|---|
| `pieces[]` (obligatoire, 2000 au plus) | une pièce par entrée ; une pièce sans `id` lisible, d'une autre catégorie ou en double est écartée et comptée |
| `pieces[].id` (`^[A-Za-z0-9_-]{1,64}$`, unique) | `items.legacy_id` : réimporter met la pièce à jour, sans doublon |
| `pieces[].name` (80 caractères au plus) | `items.name` ; vide : « Haut », « Veste » ou « Bas » |
| `pieces[].category` (`haut`, `veste`, `bas`) | `items.category` (mêmes valeurs ; `robe`, `chaussures` et `accessoire` n'existent pas dans ce format) |
| `pieces[].color` (`#RRGGBB` ou null) | `items.color` |
| `pieces[].warmth` (`leger`, `moyen`, `chaud` ; `moyen` par défaut) | `items.warmth` : 1, 2 ou 3 |
| `pieces[].occasions` (`quotidien`, `detente`, `habille`, `sport`) | `items.styles` : `quotidien` et `detente` deviennent `decontracte` ; `habille` et `sport` gardent leur nom ; vide : `decontracte` |
| `pieces[].rain` | `items.rain_ok` |
| `pieces[].status` (`dispo`, `sale`, `pressing` ; absent : `dispo`) | `items.dirty` = `status` différent de `dispo` |
| `pieces[].cutout` (PNG transparent, vêtement seul) | `items.cutout_path`, sous `<user_id>/import/<id>-cutout.png`. **Seule image propre du vêtement** : c'est elle que le miroir empile |
| `pieces[].photo` (JPEG, PNG ou WebP, facultative) | `items.photo_path`, sous `<user_id>/import/<id>-photo.<ext>`, gardée telle quelle : jamais détourée à l'import (ce peut être une photo portée). Sans `cutout`, la fiche est marquée « Photo à refaire » |
| `pieces[].createdAt` (date ISO, facultative) | `items.created_at` |
| `wears[]` (`date`, `haut`, `veste`, `bas`, `occasion`) | `outfit_history` : `date`, `item_ids` = pièces non nulles, `title` vide |
| `refusals[]` (`haut`, `veste`, `bas`) | `refusals.item_ids` = pièces non nulles |
| `settings.city` (`name`, `lat`, `lon`, `timezone`) | `profile.city`, `lat`, `lon`, `timezone` |
| `plans` (`date` → `haut`, `veste`, `bas`, `confirmed`) | `outfit_plans` : `date`, `item_ids` = pièces non nulles, `confirmed`. Seules les dates à partir d'aujourd'hui sont importées |
| `pieces[].align`, `settings.split`, `reference`, `weatherOverride`, `gestures`, `composites` | Ignorés (propres au premier prototype) |

Noms des images (`photo`, `cutout`) : `^[A-Za-z0-9][A-Za-z0-9._-]{0,199}$`, sans « .. ». Le type est lu dans les octets, jamais dans le nom : `cutout` doit être un PNG ; 10 Mo au plus par image (limite du bucket).

### 3.2 Import du paquet d'assemblage
Les photos portées sont préparées sur le PC par `scripts/assemblage/` (§7) : un zip qui contient `manifest.json` (`format: "mon-dressing/assemblage"`), `photos/<clé>.jpg` (photo d'origine), `photos/<clé>.webp` (photo détourée), `manches/<id>.webp` (manches d'un haut ou d'une veste sous son ourlet) et, avec la version 1 du champ `arms`, pour chaque photo d'un haut, d'une veste ou d'un bas, les couches des bras pliés `bras/<clé>.webp`, `corps/<clé>.webp` et `manches-photo/<clé>.webp` (s'il y a des manches), décrites par le champ facultatif `photos[clé].arms` du manifeste (format : `scripts/assemblage/README.md`). Un paquet sans ces couches reste valable.
- Écran d'import du téléphone, le même que pour le zip simple : le zip est ouvert dans le navigateur, chaque fichier est envoyé une seule fois dans Storage sous `<user_id>/assemblage/…` (une photo partagée par plusieurs pièces n'est envoyée qu'une fois), puis le serveur reçoit les fiches et les chemins (moins de 4 Mo). Limites : 500 Mo par fichier choisi, 5 Mo de manifeste, 300 pièces et 300 photos, 10 Mo par image.
- Couches des bras pliés : envoyées avec leur photo, à des chemins fixes, `<user_id>/assemblage/bras/<clé>.webp`, `corps/<clé>.webp` et `manches-photo/<clé>.webp`. `items.assembly.photo.arms` reprend le champ du manifeste, avec ces chemins Storage. Des bras pliés illisibles font refuser le paquet ; relus en base, ils sont ignorés et la pièce se dessine sans eux.
- Chaque pièce est rangée par `legacy_id` (l'`id` de `catalogue.csv`) : rejouer l'import met les fiches à jour, sans doublon. Le nom, la catégorie, la couleur, la chaleur, les styles et « ok pluie » viennent alors du paquet : **le catalogue du PC fait foi** (`dirty` et `created_at` sont gardés). Les fichiers qu'une pièce mise à jour ne cite plus ne sont supprimés qu'une fois tous les envois écrits (un envoi suivant peut citer une photo qu'un envoi précédent a cessé de citer), et jamais si un envoi a échoué.
- Supprimer une pièce ne supprime un fichier de Storage que si aucune autre pièce ne l'utilise.

## 4. Écrans
1. **Miroir (écran principal, tablette)**
   - Fond noir.
   - En haut : date, puis météo et températures du jour, comme sur le téléphone : « Pluie · 9° à 14° » (« Pluie probable » si la pluie ne vient que de la probabilité ; « Météo indisponible » sans météo, en 32 px gris dans la même hauteur, pour que la silhouette ne bouge pas). Sans réseau, « · hors ligne » en 32 px gris au bout de la date (avec « Demain · », toute la ligne passe en 32 px pendant la coupure pour tenir sur une ligne), jusqu'à la première réponse du serveur.
   - Caméra refusée : « Caméra refusée : gestes coupés. » ; occupée par une autre appli : « Caméra occupée par une autre appli. » ; moteur des gestes qui ne se charge pas ou ne tourne pas : « Gestes indisponibles pour l'instant. » (les bras sont la seule commande de la tablette : une panne ne doit pas passer pour un geste raté). Une seule ligne en 32 px gris, juste sous la météo, posée par-dessus la mise en page (la silhouette ne bouge pas, ses yeux restent au même point). L'en-tête fait toujours 156 px : 24 px de marge en haut, la date (48 px), la météo juste dessous (60 px), puis 24 px libres ; la ligne y tient avec les 16 px de marge de la silhouette et finit au haut de sa toile : elle ne touche jamais la tête. Nouvel essai d'ouvrir la caméra toutes les 30 s (sauf une demande d'autorisation écartée ; moteur en échec : 30 s, 2 min, puis toutes les 10 min ; détails au §5), et le clavier marche toujours. Sans caméra : rien.
   - **Composition libre** : on compose sa tenue soi-même, sans limite de propositions, avec les gestes des bras (§5) : la main sur le côté change le haut (← → au clavier), la main au-dessus de la tête ou devant les cuisses change le bas (↑ ↓), le signe V fait défiler les vestes (sans veste, puis les vestes ; V au clavier). Les hauts, les bas et les vestes défilent des mieux adaptés au jour visé (même score que §6 : chaleur, pluie, port récent ; pièces au sale exclues) aux moins adaptés, en boucle. Les robes viennent après les hauts : avec une robe, ↑ ↓ ne fait rien et la robe se montre seule. La veste est mise d'office quand il en faut une (§6), la meilleure ; on peut la changer ou l'enlever. Point de départ : la tenue prévue pour ce jour s'il y en a une, sinon la meilleure tenue de generateOutfits. Quand les données sont relues, la composition affichée reste (une pièce passée au sale est remplacée par celle du point de départ) ; mais si le jour visé change (heure du soir, minuit), à 4 h (météo du matin relue) ou si la tenue prévue change (choisie sur le téléphone), on repart du point de départ. Un changement fait sur le téléphone (pièce au sale ou propre, ajoutée, modifiée ou supprimée, tenue gardée sur Demain, tenue remise ou « Recommencer le choix », ville, heure du soir) arrive sur le miroir en 30 s au plus, sans rien afficher de plus (§7 bis). Si une pièce de la tenue prévue est passée au sale, elle est remplacée et le point de départ reste « Prévue ». Une tenue est toujours (haut + bas) ou robe : sans bas propre, seules les robes défilent ; sans haut ni robe, « Aucune tenue disponible ». « Oui » enregistre ce qui est affiché (pour demain, elle devient aussitôt « Prévue » ; pour aujourd'hui, « Choisie ») ; « non » enregistre le refus de ce que l'on voit (§6) puis montre une autre image : le haut suivant (sinon le bas suivant, sinon une veste), ou, quand une veste cache le haut, le bas suivant (sinon la veste suivante, ou sans veste). Une combinaison refusée reste visible en parcourant, avec « Écartée ». Un second « non » moins de 300 ms après le premier est ignoré (double appui).
   - **Retours en texte, sans mouvement** : un geste ou une touche qui ne peut rien changer le dit 1,5 s sur la ligne d'état, en 32 px graisse 400, à la place de « Choisie », « Prévue » ou « Écartée » : « Une robe se porte sans bas » (↑ ↓ avec une robe), « Aucune veste propre », « Un seul haut propre », « Un seul bas propre », « Une seule robe propre ». La phrase s'efface au geste ou à la touche suivante ; la légende du bas ne change pas. Quand un geste ne change que la pièce cachée (← → sous une veste, la veste sur une robe), « Sous la veste : … » (ou « Par-dessus : … ») passe en blanc une seconde. Après un « non », « écartée » prend 1,5 s la place du poing et du mot « non » dans la légende du bas, centré sur eux. Les fondus et l'éclat des icônes restent à régler derrière la vitre **[À mesurer]**.
   - Au centre : la tenue composée, **assemblée à partir des photos portées** (le haut d'une photo, le bas d'une autre, §7), sur fond noir. Une tenue dont une pièce n'a pas de photo portée s'affiche avec les images détourées des pièces empilées, ou leur nom. Jamais une photo rectangulaire avec son fond : à travers le miroir, le fond s'allumerait. Jamais de trou noir non plus : tant que la nouvelle silhouette n'est pas dessinée, l'ancienne (ou les pièces empilées d'avant) reste à sa place, pâlit (opacité 0,4, sans transition) si l'attente dépasse 300 ms, sans se rallumer à l'appui suivant, puis la nouvelle la remplace ; pendant ce temps, « oui » et « non » ne font rien (on n'enregistre jamais une tenue qu'on n'a pas vue ; un pouce ou un poing tenu ne remplit pas son anneau pour rien : le maintien commence une fois la silhouette dessinée, sans avoir à relâcher), les flèches et la veste restent libres.
   - Sous la tenue, la légende de ce que montre la silhouette, une pièce par ligne (la veste et le bas, le haut et le bas, ou la robe), puis la pièce cachée en plus petit (« Sous la veste : … », « Par-dessus : … ») ; puis, juste après la dernière ligne, « Choisie » si c'est la tenue acceptée ce matin, sinon « Prévue » si c'est la tenue prévue, sinon « Écartée » si elle a été refusée (pas de compteur). Sa hauteur est réservée en un seul bloc : 176 px sous une silhouette (deux lignes, la note et l'état), 184 px sous des pièces empilées (trois lignes et l'état) ; la silhouette garde la même taille d'une tenue à l'autre (812 px de haut), les yeux au même point. Après « oui », « Bonne journée » ou « Prête pour demain » prend la place de cette légende, dans la même hauteur : la tenue et la légende du bas restent affichées.
   - Lisible à 1–2 m derrière la vitre : trois tailles de texte (52, 40 et 32 px), en blanc ou gris clair (#ccc), jamais plus fin que 400. En haut : « Demain · mardi 27 octobre » sur une ligne, puis la météo, le plus gros texte.
   - En bas : indicateurs « ← → haut  ⇅ bas  V veste  oui  non » (icônes de 40 px ; « veste » et son V, seulement les jours où une veste propre peut être proposée ; les cinq tiennent sur une ligne, 678 px au plus dans la zone utile de 40 à 760 px), avec des **icônes au trait** (V, pouce, poing) et **non des emojis**, interdits par la charte de l'app (AGENTS.md). Le V est montré parce que, sans lui, le geste de la veste ne se devine pas. Pour lui faire de la place, « écartée » prend la place du poing et de « non » au lieu de déborder à droite de « non ».
   - **Anneau de progression** pendant un geste tenu (§5) : un cercle au trait, blanc, de 50 px, autour de l'icône du geste (V pour « veste », pouce pour « oui », poing pour « non »), à 10 px du mot qui suit (16 px entre le V, le pouce ou le poing et son mot, 12 px après les flèches, 22 px entre les groupes : la ligne garde sa largeur), qui se remplit pendant la seconde de maintien, dans le sens des aiguilles d'une montre ; un jour sans veste propre, « veste » n'est pas dans la légende : le V tenu n'a pas d'anneau et dit « Aucune veste propre ». Toujours au même endroit, il ne cache ni le visage ni la légende ; pas d'autre animation (ni transition, ni éclat).
   - Sans session (premier lancement, session perdue) : « Tablette non connectée » en 32 px gris, puis un lien « Se connecter » en blanc, sans cadre, à toucher avant de monter la tablette ; il ouvre `/connexion?depuis=miroir`, qui ramène au miroir une fois la tablette connectée.
   - **Veille par présence** : après 2 min sans personne devant le miroir ni touche, n'afficher que l'heure, grande (140 px), en gris moyen de 7 h à 22 h et très sombre la nuit (valeurs à régler derrière le vrai miroir **[À mesurer]**). « Quelqu'un » : PoseLandmarker voit ses deux épaules (§5) ; tant que la personne est là, l'écran reste allumé. Une personne qui arrive réveille l'écran, et rien d'autre : l'image qui réveille ne déclenche aucun geste, et les gestes commencés sont oubliés (un pouce déjà levé ne compte pas : il faut le relâcher ; une main déjà devant la poitrine doit en sortir avant de s'armer). Rien ne se déclenche pendant la veille. La veille vaut aussi pendant le test des touches (il garde son étape et les touches choisies ; la touche qui réveille n'est pas enregistrée ; laissé en plan, il est fermé sans rien enregistrer à la relecture de 18 h, minuit ou 4 h qui tombe pendant la veille, §5) et sur les écrans de problème (« Serveur injoignable… », heure dans le fuseau de l'appareil, nouvel essai toutes les 30 s) ; quelqu'un qui arrive, une touche ou un toucher réaffiche l'écran, sans rien faire d'autre. Rien ne change pendant « Chargement… » (la caméra démarre après la première lecture). Le test des touches ouvert par `?touches=test` réveille l'écran, puis la veille revient au bout de 2 min.
   - **Préparer demain** :
     - à partir de 18 h, réglable, le miroir propose les tenues de **demain**, avec la météo de demain et le mot « Demain » au-dessus ;
     - accepter enregistre la tenue dans `outfit_plans`, avec `confirmed` à vrai, et affiche « Prête pour demain » 3 s sous la tenue, qui reste affichée ;
     - le lendemain matin, la tenue prévue est le point de départ ;
     - depuis le téléphone, on peut aussi choisir la tenue de demain (page Demain) : 5 tenues proposées (§6), la tenue prévue comprise, en grand en tête (sinon la première proposition, avec « Garder pour demain ») ; c'est aussi le point de départ du miroir. Une fois la tenue gardée, « Prévue pour demain » s'affiche à la place de « Garder pour demain ». Les autres sont par deux avec « Garder », qui fait remonter en haut. Sous chaque tenue, la légende du miroir en entier (deux lignes au plus par pièce), les pièces vues en couleur du texte et la pièce cachée en gris. Les tenues sont posées sur une plaque gris très foncé, la même en clair et en sombre (comme la photo de la fiche). Si une pièce prévue est passée au sale, une note sous la tenue dit par quoi elle est remplacée (« Pull en lin au sale : remplacé par Chemise blanche. ») ;
     - **Recommencer** (miroir et téléphone) : efface la tenue choisie pour le jour visé (et la tenue portée si c'est aujourd'hui) et les refus faits pendant ce choix (§6) ; on revient au point de départ (la meilleure tenue, sans les refus effacés), et sur le téléphone les tenues du départ reviennent, à partir de la première.
       - Sur le miroir, deux appuis sur la touche R d'un clavier (« Recommencer » n'a pas de geste : sans clavier, il se fait depuis le téléphone) : le premier affiche « Appuie encore pour recommencer » 3 s, le second affiche « On recommence » 1,5 s. Pendant ces deux messages, la tenue est cachée : tout autre défilement ou touche efface seulement le message ; un geste tenu (pouce, poing, V) n'y commence pas, puisque la légende et son anneau sont cachés. L'écran change tout de suite ; la requête part par la file d'envoi (§7 bis), avec les refus faits sur la tablette (30 au plus).
       - Sur le téléphone (page Demain), le bouton « Recommencer le choix » apparaît sous la tenue en tête quand il y a quelque chose à effacer, dit ce qui sera effacé et demande une confirmation. Si la page a changé de jour (restée ouverte après minuit), rien n'est effacé et elle demande d'être rechargée. Le miroir le voit en 30 s au plus (§7 bis).
2. **Garde-robe** (ouverte depuis le téléphone, pas la tablette) : grille des vêtements, ajout par photo, au sale oui ou non. Vignette d'une pièce assemblée : la zone de sa photo portée qui la montre (le haut pour un haut ou une veste, le bas pour un bas, la photo entière pour une robe).
   - Une catégorie à la fois, choisie en haut (menu de catégorie, collé sous la ligne retour avec « Marquer au sale » à droite) et gardée dans l'adresse (`?categorie=bas`). Sous Accessoires et Chaussures : « Pas proposés sur le miroir. ». Le compte (« 24 pièces · 3 au sale ») est une petite ligne grise sous le titre.
   - « Marquer au sale » : toucher une vignette la met au sale ou la remet propre, jusqu'à « OK », qui reste à portée en faisant défiler. « 3 au sale » ouvre les seules pièces au sale : toucher une pièce la remet propre (la retoucher la remet au sale), sur place ; « Tout est lavé », en bas, les remet toutes propres.
   - Au retour d'une fiche, la grille revient à la même catégorie et au même endroit. Une URL signée d'affichage est resservie pendant 30 min : un nouveau rendu ne retélécharge pas les photos.
   - Fiche d'une pièce : « Enregistrer » en haut à droite, grisé tant que rien n'a changé ; on reste sur la fiche (« Enregistré. »). Pas de « Changer la photo » sur une pièce assemblée : elle se change en réimportant le paquet (§3.2), et le serveur refuse aussi. Sur les autres pièces, « Changer la photo » suit le même chemin que l'ajout (écran 3), PNG déjà détouré compris.
3. **Ajout d'un vêtement** (téléphone). Deux façons d'avoir ses vêtements dans l'app :
   - **mode silhouette** : une **photo portée sur fond vert**, même endroit, même pose, bras le long du corps, en ne changeant qu'une pièce à la fois (§7). Ces photos sont préparées sur le PC puis importées (§3.2) ; l'ajout d'une photo portée directement depuis le téléphone est une étape à venir (§10) ;
   - **mode simple** : une photo à plat par pièce, depuis l'écran Ajouter, en cinq temps (ou un zip `Dressing/`, §3.1) :
     1. photo prise au téléphone ou choisie dans la galerie. Elle est réduite dans le navigateur à 1600 px de côté au plus, en JPEG qualité 0,85 sur fond blanc, puis envoyée directement dans le bucket privé `items` (`<user_id>/<uuid>.jpg`) avec la session du compte. Le serveur ne reçoit que le chemin (limite Vercel de 4,5 Mo, Claude refuse les images de plus de 5 Mo). **PNG déjà détouré** : si le fichier choisi est un PNG qui peut avoir de la transparence (canal alpha ou tRNS), le navigateur envoie en plus le PNG réduit, transparent, sous `<user_id>/<uuid>-cutout.png`, à condition qu'il ait au moins 1 % de pixels d'alpha nul et au moins un pixel opaque (PNG non entrelacé, 8 ou 16 bits, gris+alpha ou RGBA, 4096 px de côté au plus). Seul un PNG est concerné, ni WebP ni HEIC ;
     2. détourage côté serveur. Un PNG déjà détouré est retéléchargé et revérifié avec la même règle : s'il est bon, il devient le détourage, fal.ai n'est pas appelé et rien n'est dépensé ; sinon il est effacé (s'il ne sert à aucune pièce) et la photo suit le chemin habituel. Chemin habituel : Bria RMBG 2.0 sur fal.ai (`fal-ai/bria/background/remove`, environ 0,018 $ l'image), seulement si `FAL_KEY` est présente ; sinon « Détourage indisponible : FAL_KEY absente. Une photo PNG déjà détourée (fond transparent) passe sans elle. » ;
     3. la Claude API remplit la fiche (nom, catégorie, couleur, chaleur, styles, ok pluie) en sortie structurée JSON (`output_config.format` avec un schéma), seulement si `ANTHROPIC_API_KEY` est présente. Modèle : `claude-opus-5-5`, dans une constante `CLAUDE_MODEL` de `lib/server/claude.ts`, à reprendre pour les titres du §6 quand ils seront codés. N'utilise aucun autre identifiant de modèle de mémoire ;
     4. on corrige la fiche (pendant l'attente : « Détourage et fiche en cours… », ou « Fiche en cours… » pour un PNG déjà détouré) ;
     5. on enregistre ; la fiche de la pièce s'ouvre.
4. **Réglages** (téléphone) :
   - ville, heure du soir de « Préparer demain » ; « Tenues écartées » (§6) ;
   - pas de bloc « Manette » : le test des touches d'un clavier de secours ne s'ouvre que sur la tablette, par `?touches=test` (§5) ;
   - à venir : sensibilité des gestes, caméra on/off.

**Connexion**
- Un seul compte Supabase, créé une fois à la main dans le tableau de bord ([supabase.md](supabase.md)).
- Inscriptions fermées : Supabase > Authentication > « Allow new users to sign up » désactivé, et `signInWithOtp({ email, options: { shouldCreateUser: false } })`.
- Le serveur n'accepte que l'id `ALLOWED_USER_ID`. Sans ça, n'importe qui pourrait créer un compte par l'URL publique et dépenser le budget Claude et fal.ai.
- La tablette se connecte **une fois, avant d'être montée** derrière le miroir, et reste connectée : les refresh tokens n'expirent pas. N'active pas « Single session per user ».
- Ouverte depuis le miroir (« Se connecter », `/connexion?depuis=miroir`), la connexion ramène au miroir, par le mot de passe comme par le lien ; sinon, à l'accueil du téléphone. Table fixe (`miroir` → `/`, tout le reste → `/gestion`), jamais une adresse lue dans l'URL. Pour le lien, le formulaire pose un cookie court (`connexion-depuis=miroir`, chemin `/auth`, 1 h), que `/auth/callback` lit puis efface : l'adresse du lien reste `…/auth/callback`, celle déclarée dans les Redirect URLs (Supabase compare toute l'adresse, query comprise). Un lien ouvert dans un autre navigateur mène à la connexion sans retour au miroir.
- **Connexion par adresse e-mail et mot de passe** (`signInWithPassword`), sur le téléphone comme sur la tablette. Le mot de passe est choisi une fois, à la création du compte dans Supabase. Raison : le service d'e-mail par défaut de Supabase n'envoie que 2 e-mails par heure, et seulement aux adresses de l'équipe du projet Supabase ; un lien grillé ou expiré bloque la connexion. Après la connexion, le navigateur appelle `/api/me` et déconnecte tout compte autre que `ALLOWED_USER_ID`.
- Le lien magique reste proposé en secours (« Recevoir un lien par e-mail »).
- Avec `@supabase/ssr` (flux PKCE), **le lien ne marche que dans le navigateur qui l'a demandé**. Pour connecter la tablette par le lien, ouvre l'e-mail sur la tablette elle-même, dans Chrome. Un lien ouvert ailleurs mène au message « Ouvre le lien dans le navigateur où tu l'as demandé ».
- **Évite une boîte Outlook/Hotmail pour le lien magique** : son analyseur ouvre chaque lien avant toi, et le lien à usage unique est alors déjà consommé (l'app affiche « Ce lien n'est plus valable. Demande-en un nouveau. »). Le mot de passe n'a pas ce problème. Un code à 6 chiffres éviterait le problème, mais il faut modifier le modèle d'e-mail, ce que Supabase n'autorise qu'avec un serveur d'envoi (SMTP) personnalisé.

## 5. Contrôles (aucun tactile sur la tablette, pas de manette)
Le miroir se commande avec les **mouvements des bras**, devant la caméra frontale de la tablette. Un clavier reste en secours, avec les touches de PC par défaut (PC, tests). Le mode d'emploi : [gestes.md](gestes.md).

| Action | Geste (vu de la personne face au miroir) | Touche de PC (secours) |
|---|---|---|
| Haut suivant | Main devant la poitrine, puis sortie sur le côté, **à sa droite** | → |
| Haut précédent | Main devant la poitrine, puis sortie sur le côté, **à sa gauche** | ← |
| Bas suivant | Main devant la poitrine, puis **au-dessus de la tête** | ↑ |
| Bas précédent | Main devant la poitrine, puis **vers le bas, devant les cuisses** | ↓ |
| Veste suivante (sans veste, puis chaque veste) | **Signe V** (Victory) tenu 1 s | V |
| Accepter (« oui ») | **Pouce levé** (Thumb_Up) tenu 1 s | Entrée |
| Refuser (« non ») | **Poing fermé** (Closed_Fist) tenu 1 s | Retour arrière |
| Recommencer (deux appuis, §4) | aucun geste : depuis le téléphone, ou au clavier | R |
| Réveiller l'écran | arriver devant le miroir (présence) | n'importe quelle touche |

**Défilements : la méthode des zones** (validée en conditions réelles lors d'un essai de calibration). Les valeurs de l'essai font foi ; elles sont des constantes nommées dans `lib/gestures/constants.ts`.
- Repères de PoseLandmarker lite : épaules 11/12, coudes 13/14, poignets 15/16, index 19/20, hanches 23/24, genoux 25/26. La main est le milieu poignet – index, vue si les deux ont une visibilité ≥ `MIN_VISIBILITY` (0,5). Les repères sont lissés pour les zones : `ZONE_SMOOTHING` = 0,75 de la nouvelle image. Les x sont remis à l'échelle des y (largeur / hauteur de l'image) : même résultat en portrait et en paysage.
- Unités du corps : la **demi-largeur d'épaules** pour l'horizontale, la **longueur de buste** (milieu des épaules → milieu des hanches) pour la verticale. Position horizontale : u = −(x main − milieu des épaules) / demi-largeur d'épaules ; l'image brute de la caméra frontale n'est pas inversée, donc u > 0 est **à sa droite**.
- Épaules ou hanches mal vues (visibilité < `BODY_VISIBILITY`, 0,6) : aucun geste, les mains armées reviennent au repos (« Recule » dans le debug).
- **De profil** (ajouté après un essai filmé) : les épaules se superposent dans l'image, la demi-largeur d'épaules s'effondre et u n'a plus de sens (jusqu'à 19,9 pour une main près du corps : de faux défilements). Une image où la demi-largeur d'épaules est sous `MIN_SHOULDER_RATIO` = 0,2 longueur de buste compte comme un corps mal vu : aucun geste, mains au repos (« De profil » dans le debug). De face, ce rapport vaut 0,30 à 0,35 (1 % des images sous 0,23) ; les faux défilements de l'essai partaient à 0,16 et 0,18. La garde est image par image (pas de fenêtre) : un creux d'une image entre deux gestes ne les empêche pas.
- **Devant la poitrine** (|u| < `CENTER_IN` = 0,8, de `BAND_TOP` = 1,2 longueur de buste au-dessus des épaules jusqu'à la taille) : la main **s'arme** (`ARM_FRAMES` = 1 image suffit, un balayage rapide compte). Revenir au buste ne déclenche rien : ça réarme. La **taille** est à `WAIST` = 0,62 longueur de buste sous les épaules (≈ nombril). Correction faite sans changer de constante : cette zone monte plus haut que la ligne du haut, et une main levée tout droit au milieu s'y réarmait à chaque image, donc « bas suivant » ne partait jamais. Une main **déjà armée** ne s'y réarme plus au-dessus de la ligne du haut ; une main au repos s'y arme comme dans l'essai.
- Depuis armée, la main déclenche quand elle reste `EXIT_FRAMES` = 2 images de suite dans une zone d'action, et plus de `GESTURE_COOLDOWN_MS` = 500 ms après le défilement précédent (des deux mains) ; elle revient alors au repos :
  - **sur le côté** : |u| > `SIDE_OUT` = 1,3, mouvement plus horizontal que vertical (`HORIZONTAL` = 1,2), entre la ligne du haut et celle du bas : à sa droite haut suivant, à sa gauche haut précédent ;
  - **au-dessus de la tête** : au-dessus de la ligne du haut (`UP_LINE` = 0,65 longueur de buste au-dessus des épaules), mouvement plus vertical, pour une main armée sous la ligne des épaules (devant la poitrine même, pas devant le visage) : bas suivant. Une main qui flotte à hauteur de la ligne ne défile donc qu'une fois ; il faut repasser devant la poitrine. **[À mesurer]** : une main passée devant la poitrine puis posée au-dessus du haut de la tête (se recoiffer) dépasse la ligne et donne aussi « bas suivant » ; posée sur la tête, sous la ligne, rien ;
  - **devant les cuisses** : sous la ligne du bas (`DOWN_LINE` = 0,2 longueur de buste sous les hanches), mouvement plus vertical, à moins de `THIGH_FRONT` = 1,6 demi-largeur de hanches du milieu des hanches : bas précédent. Les bras qui retombent sur les côtés ne comptent pas. **[À mesurer]** : d'après des proportions moyennes (à régler sur soi avec `?gestures=debug`), une main tendue devant les cuisses n'atteint qu'environ 1,22 longueur de buste sous les épaules, à 1 ou 2 cm de la ligne du bas (1,2), et une main le long du corps tombe vers 1,25 ; un bras qui retombe d'abord devant soi, puis s'écarte, passe sous la ligne près du milieu des hanches et donne « bas précédent » (rien ne le distingue du geste avec la méthode validée).
- **Bras au repos le long du corps : jamais rien.** Ajouté après l'essai : une main armée revient au repos quand son bras retombe le long du corps (sous la taille, hors de la zone des cuisses, et sous la ligne du bas ou par un mouvement surtout vertical : une sortie sur le côté commencée au nombril, qui passe sous la taille en sortant, défile), ou quand elle n'est pas repassée devant la poitrine depuis `ARM_TIMEOUT_MS` = 1 s (sur des journaux de gestes rejoués, la dernière image devant la poitrine précède presque toujours le défilement de 0,1 à 0,9 s ; les rares cas au-delà, deux bras levés au-dessus de la tête puis redescendus en s'ouvrant, ou une main qui annulait le geste de l'autre, sont annulés, et c'est voulu) ; après un défilement, l'autre main revient au repos si elle a déjà quitté la poitrine (deux bras ouverts en grand : un seul défilement), et après « bas suivant » ou « bas précédent », elle est bloquée si elle est encore armée devant la poitrine (deux mains levées tout droit ensemble, l'une un peu après l'autre, ne défilent qu'une fois ; bloquée, elle doit sortir de la zone de la poitrine avant de se réarmer) ; une image sans personne à moins de `POSE_GAP_MS` = 300 ms de la dernière où on l'a vue ne change rien (PoseLandmarker la perd un instant pendant un mouvement rapide).

**Gestes tenus** (MediaPipe Gesture Recognizer, lus par `categoryName`, jamais par `index`) : pouce levé = oui, poing fermé = non, signe V = veste suivante.
- Main levée au-dessus de la taille, à peu près immobile (à moins de `HOLD_STILL` = 0,5 demi-largeur d'épaules de son départ), score ≥ `HOLD_MIN_SCORE` = 0,6, tenue `HOLD_MS` = 1 s : le geste se valide à une image où le Gesture Recognizer le voit encore, 1 s ou plus après le début. Une image hésitante (autre catégorie, image où il ne tourne pas, personne ou corps mal vu un instant) est pardonnée pendant `HOLD_GRACE_MS` = 300 ms : le maintien survit, mais un geste relâché ne se valide jamais pendant ce délai (l'anneau s'arrête, puis s'efface). La main reconnue est celle du corps la plus proche (`HOLD_MATCH`).
- L'**anneau de progression** se remplit pendant la seconde (§4), sans jamais se fermer avant la validation (il s'arrête à 95 %, puis disparaît quand le geste part) : un geste relâché juste avant la seconde ne montre pas un anneau plein sans « oui ». Après un geste tenu validé : `HOLD_PAUSE_MS` = 1,5 s sans geste tenu, il faut relâcher le geste pour le refaire, et les mains sont bloquées jusqu'à ce qu'elles quittent la poitrine : un geste tenu ne déclenche jamais aussi un défilement en repartant, et un défilement ne déclenche jamais un geste tenu (il annule le maintien en cours, et aucun ne commence dans les 500 ms). La main qui a défilé ne tient pas de geste avant d'être revenue devant la poitrine sous la ligne du haut (la zone de la poitrine monte au-dessus, là où part « bas suivant ») ou sous la taille ; de même pour l'autre main quand elle a suivi le mouvement (deux poings levés au-dessus de la tête : « bas suivant » seulement, pas « non »). Restée devant la poitrine, l'autre main peut tenir un geste. Pendant un message qui cache la tenue (« Appuie encore pour recommencer », « On recommence », « Touches enregistrées »), aucun geste tenu ne commence : la légende et son anneau sont cachés ; un défilement efface le message.
- Mêmes garde-fous que les touches : « oui » et « non » ne font rien tant que la silhouette affichée n'est pas celle de la légende (§4) ; leur maintien ne commence pas (pas d'anneau), un maintien en cours s'arrête et repart de zéro une fois la silhouette dessinée, sans relâcher ; le V reste libre. Un second « non » moins de 300 ms après le premier est ignoré, et les retours en texte (« écartée », « Choisie »…) sont les mêmes.

**Présence et veille** (§4)
- Quelqu'un est là quand PoseLandmarker voit ses deux épaules (visibilité ≥ `PRESENCE_VISIBILITY` = 0,5), sur l'image même. Sa présence compte comme une activité : la veille vient 2 min après la dernière image avec quelqu'un ou la dernière touche.
- Une personne qui arrive réveille l'écran ; l'image (ou la touche) qui réveille ne fait rien d'autre, et les gestes commencés sont oubliés jusqu'à ce qu'ils soient relâchés, même ceux que le Gesture Recognizer n'a pas encore vus (il ne tourne qu'une fois une main vue levée) : les deux mains sont bloquées (une main déjà devant la poitrine doit en sortir avant de s'armer, une main ailleurs se débloque à l'image suivante), et un pouce, un poing ou un V déjà faits ne comptent qu'une fois relâchés (main redescendue sous la taille, ou ni pouce, ni poing, ni V sur une main levée). De même à la reprise de la caméra et en revenant d'un écran qui n'accepte pas de geste. Rien ne se déclenche pendant la veille, pendant « Chargement… », sur les écrans de problème ni pendant le test des touches (les gestes y sont oubliés au fur et à mesure : rien ne part en revenant à la composition).

**Économie** (GPU de la tablette pas encore mesuré **[À mesurer]**)
- PoseLandmarker lite à `POSE_FPS_IDLE` = 5 images/s sans personne, jusqu'à `POSE_FPS_PRESENT` = 30 images/s quand quelqu'un a été vu dans la dernière seconde ; Gesture Recognizer seulement quand une main est levée au-dessus de la taille (corps bien vu), à `RECOGNIZER_FPS_MAX` = 10 images/s au plus, sur la même image.
- Délégué GPU, CPU en secours : aussi en cours de route si le GPU échoue, et d'emblée sans WebGL ou sur un moteur WebGL logiciel (SwiftShader, llvmpipe, WARP : le délégué GPU y « marche » mais rame, 2,2 images/s contre 16,6 sur le CPU d'un PC de développement). Sur le GPU, les `GPU_PROBE_FRAMES` = 15 premières images avec quelqu'un devant sont chronométrées : au-delà de `GPU_SLOW_MS` = 40 ms par image en médiane pour PoseLandmarker, passage au CPU, une fois pour toutes, c'est-à-dire jusqu'au prochain chargement de la page, même après un échec du moteur sur le CPU (de même pour un GPU qui échoue en cours d'analyse, ou au chargement quand le CPU, lui, se charge) **[À mesurer]** (seuil tiré d'un PC de développement : vrai GPU 6,5 ms, CPU 17,6 ms ; sur une tablette, le CPU pourrait être plus lent qu'un GPU « lent »).
- Le premier appel de chaque modèle bloque la page (sur un PC de développement : 2,2 à 2,5 s pour PoseLandmarker, 1,2 s pour le Gesture Recognizer). Il se fait au chargement, sur une image noire de 640×480 (aucune image de la caméra), quand la page est libre, avant que les gestes ne démarrent : jamais sur la première image analysée ni au premier bras levé.
- L'analyse part juste après le dessin de l'image d'écran : elle ne retarde pas l'affichage d'une nouvelle silhouette, et le passage de 5 à 30 images/s ne fait pas saccader le miroir (§7 bis).

**Caméra**
- Caméra frontale (`facingMode: user`, ~640×480, sans son), seulement sur l'écran du miroir « / », ouverte après la première lecture des données. Une seule partie de l'app la tient ; elle est rendue quand la page est cachée (`visibilitychange`) et reprise au retour. L'écran de secours (§8) ne la tient pas : seule une touche le réveille.
- MediaPipe Tasks Vision (`@mediapipe/tasks-vision`), **tout en local** : le moteur (`/mediapipe/wasm`, copié du paquet npm) et les modèles (`/mediapipe/models/*.task`, téléchargés une fois depuis les adresses officielles de Google et vérifiés par leur empreinte SHA-256) sont préparés par `scripts/mediapipe-assets.mjs` avant `next dev` et `next build`, puis servis par l'app elle-même, sans CDN ni service externe à l'usage ; import dynamique, côté navigateur seulement, en mode VIDEO. Si le téléchargement échoue, le build s'arrête avec un message clair ; `npm run dev` continue avec un avertissement (le miroir marche alors au clavier, sans gestes).
- **Vie privée** : l'image de la caméra ne quitte jamais l'appareil (§9) ; elle n'est ni envoyée, ni enregistrée, ni affichée, même en debug. La vidéo n'est pas dans la page : MediaPipe n'en tire que des repères. Aucune vidéo de personne dans git, les tests ou les captures (les tests e2e utilisent la mire de la fausse caméra de Chromium).
- Caméra refusée : « Caméra refusée : gestes coupés. » ; occupée par une autre appli (`NotReadableError` : une visio ou un logiciel de webcam la tient déjà) : « Caméra occupée par une autre appli. » ; moteur des gestes qui ne se charge pas (modèle ou moteur introuvable, mémoire) ou qui échoue aussi sur le CPU : « Gestes indisponibles pour l'instant. » ; pas de caméra : rien. Une seule petite ligne grise sous la météo (§4), et le clavier marche toujours. Nouvel essai toutes les 30 s (une demande d'autorisation écartée n'est pas rouverte toutes les 30 s : on attend que l'autorisation change). Moteur en échec : chaque essai recharge et recompile tout le moteur, donc les essais s'espacent comme l'écran de secours (§8), 30 s, 2 min, puis toutes les 10 min (le compte repart de zéro après `ENGINE_STABLE_MS` = 5 min de marche sans panne : un moteur qui repart puis retombe ne revient pas aux essais toutes les 30 s, qui bloquent la page 2 à 3,5 s chacun), et le moteur se charge avant la caméra : tant qu'il manque, la caméra (et son témoin, derrière la vitre) ne s'allume pas.
- **Vidéo figée** : la caméra « tourne », mais la vidéo ne donne plus d'image depuis `CAMERA_STALL_MS` = 5 s (sur Android, une autre appli qui prend la caméra rend souvent la piste muette au lieu de la terminer ; une vidéo hors de la page peut aussi cesser de produire des images). Elle est rendue puis rouverte ; au troisième blocage de suite (`CAMERA_STALL_LIMIT`, moins d'une minute entre deux), la ligne du miroir le dit (« Caméra occupée par une autre appli. » si la piste est muette, sinon « Gestes indisponibles pour l'instant. ») et un nouvel essai suit ; un blocage moins d'une minute après le précédent la redit aussitôt, sans rouvrir la caméra trois fois de plus. Une caméra ouverte qui ne donne aucune première image (la vidéo ne démarre pas) est rendue au bout de `CAMERA_STALL_MS` et signalée de même, avec un nouvel essai. Pendant un nouvel essai après un problème (refusée, occupée, gestes indisponibles), la ligne reste jusqu'à ce que la vidéo avance vraiment : elle ne disparaît pas pour une caméra rouverte mais toujours muette ou figée. Plus d'une seconde entre deux images d'écran (page gelée) ne compte pas, et une page cachée pendant l'ouverture de la caméra n'est pas une panne.
- `?gestures=debug` sur « / » : sur noir, en haut le texte (sous la ligne de la caméra), dessous le cadre de l'image analysée (sans l'image ; aucun de ses traits ne traverse le texte), les zones (poitrine, côtés, lignes du haut, du bas et de la taille, cuisses), les mains (point plein : armée ; cercle : au repos ou bloquée), retournés comme un miroir ; en texte, le délégué GPU/CPU, les images/s de PoseLandmarker et du Gesture Recognizer (d'après l'intervalle moyen de la dernière seconde), la présence (« Personne », « Présente », « Recule », « De profil »), le geste reconnu et son score, l'état des mains (entre parenthèses, le |u| le plus petit de leur dernier armement : armée de justesse près de 0,8, ou bien au centre) et le dernier geste parti ; quand le miroir affiche déjà sa ligne de la caméra (refusée, occupée, gestes indisponibles), le debug ne la répète pas par-dessus. Pour régler les seuils derrière le miroir. Avec `?gestures=debug`, l'anneau de progression peut aussi être dessiné sans geste (`window.monDressingGestures`, pour les tests e2e : la fausse caméra ne montre jamais de pouce).

**Touches (clavier de secours)**
- Les touches de PC par défaut : ← → ↑ ↓, V, Entrée, Retour arrière, R. Une touche présente dans `profile.key_map` suit toujours `key_map` ; les touches de PC servent quand elles n'y figurent pas.
- Un `key_map` vide ou incomplet **n'ouvre jamais** de lui-même le test des touches (une tablette neuve y resterait bloquée). Le « Test des touches » ne s'ouvre que par `?touches=test` sur la tablette (pas de bouton sur le téléphone) ; `?touches=test` quitte l'adresse dès l'ouverture du test : un rechargement de la page (écran de secours) ne le rouvre pas. Une tablette sans clavier laissée sur le test en sort à la relecture suivante de 18 h, de minuit ou de 4 h qui tombe pendant la veille : le test est fermé sans rien enregistrer (les gestes n'y font rien et la page ne se recharge pas d'elle-même : rien d'autre ne l'en ferait sortir). Éveillé, quelqu'un le fait : il reste ouvert. Mode guidé : la tablette affiche « Appuie sur la touche pour : Haut suivant » et, dessous, la touche conseillée (« flèche droite → » : « haut » et « bas » y désignent des vêtements, pas des flèches), enregistre `event.code` et `event.key`, puis passe à l'action suivante. L'écran affiche aussi en direct ce que reçoit l'app, en mots (« Reçu : flèche droite », « D », « Maj » ; le code brut seulement pour une touche inconnue), et dessous les touches déjà choisies ; la consigne, calée en haut, ne bouge pas quand cette liste s'allonge. À la fin, « Touches enregistrées » : la tenue n'a pas encore été vue, « oui » et « non » effacent seulement ce message. Le serveur exige les quatre actions de base ; les autres (bas, veste, recommencer) restent facultatives.
- Une touche qui réveille l'écran ne déclenche rien d'autre.

**Tests** : la reconnaissance est une machine à états pure (`lib/gestures/`), testée avec des poses synthétiques (hauteurs de proportions moyennes : main le long du corps vers 1,25 longueur de buste sous les épaules, tendue devant les cuisses vers 1,22). Les réglages de l'essai de calibration y sont repris à l'identique. Rejouer ses propres journaux de gestes (des nombres seulement, jamais d'image) est possible en local, mais aucun journal n'est fourni avec le dépôt. Ce que le miroir fait d'une image (réveil, présence, écrans qui n'acceptent pas les gestes) est pur aussi (`lib/mirror/gestures.ts`). La caméra elle-même (`components/mirror/gestures/camera.ts`) est testée sans navigateur, avec de fausses tâches MediaPipe qui échouent au chargement ou en cours d'analyse, ou rament, et une vidéo qui se fige ou ne démarre pas. Les tests e2e du projet `camera` lancent le vrai MediaPipe sur la mire de la fausse caméra de Chromium : rien ne doit se déclencher ; une vidéo figée y est rouverte, puis signalée.

## 6. Choix des tenues
- Fonction pure `generateOutfits(items, context) → Outfit[]` dans `lib/outfits/`. Elle est déterministe : mêmes entrées, même date, même résultat.
- Critères :
  - chaleur comparée à la température du jour (celle du matin pour la veste : elle sert au plus frais) ;
  - pluie ;
  - pièces au sale exclues ;
  - pièce pas portée ces 3 derniers jours ;
  - harmonie des couleurs ;
  - refus passés ;
  - variété entre les propositions, jugée sur ce que montre la silhouette (§7) : la robe, sinon la veste (ou le haut sans veste), et le bas. Le même dessus visible revient dans 3 tenues au plus, et deux tenues ne donnent jamais la même image tant qu'une autre existe (sans cette règle, un jour de pluie, la seule veste ok pluie se retrouverait dans les 5 tenues).
- Une tenue = (haut + bas) ou robe, + chaussures, + veste si le maximum est < 15 °C, s'il pleut, ou si le minimum (le matin) est < 12 °C, + accessoire optionnel.
  - Si la garde-robe n'a aucune pièce disponible d'une catégorie (chaussures, veste), la tenue s'en passe au lieu d'être écartée. Le format db.json (§3.1) n'a ni chaussures ni robes.
  - S'il y a moins de 5 combinaisons possibles, proposer celles qui existent.
- La date du jour se calcule dans `profile.timezone`, jamais en UTC (Vercel tourne en UTC).
- **Refus** : « non » vaut pour ce que l'on voit. On enregistre ce que montre la silhouette (§7) : la veste et le bas (le haut caché dessous ne compte pas), le haut et le bas sans veste, ou la robe seule. Chaussures et accessoire ne comptent pas. Une proposition est écartée si ce que montre sa silhouette est égal à un refus enregistré. Les refus au format plus ancien (pièces principales + veste) restent valables : ils écartent encore exactement ces pièces.
  - Page « Tenues écartées » (téléphone, depuis Réglages) : les refus du plus récent au plus ancien, chacun avec « Remettre », qui l'efface. Chaque refus s'écrit comme la légende du miroir, une pièce par ligne, la pièce cachée en gris (« Sous la veste : … »), et « Pièce supprimée » en gris si une pièce n'existe plus ; sans image pour l'instant.
- Proposer 5 tenues distinctes, de la meilleure à la moins bonne. Chaque tenue a un titre simple, calculé sans réseau (« Pull marine et jean brut », `lib/outfits/title.ts`). Un titre court donné par la Claude API (appel côté serveur, mis en cache par tenue, le titre simple en secours) est prévu, pas encore codé.
- Accepter enregistre dans l'historique et affiche « Bonne journée » 3 s sous la tenue, qui reste affichée, puis « Choisie ». Refuser mémorise puis montre autre chose (§4). « Recommencer » (§4) efface les refus faits pendant le choix du jour visé : ceux dont `created_at` tombait quand le miroir proposait ce jour-là (aujourd'hui, ou demain après l'heure du soir, dans `profile.timezone`), plus ceux que la tablette nomme (un refus resté en file arrive plus tard au serveur). Les autres restent ; un refus importé d'un db.json porte un `created_at` ancien et n'est jamais effacé. Limite acceptée : un refus resté en file hors ligne avant l'heure du soir et reçu après est rattaché au choix du lendemain.
- Le contexte de `generateOutfits` porte la date visée (aujourd'hui, ou demain après 18 h) et la météo de ce jour-là. Une tenue prévue dans `outfit_plans` pour cette date passe en premier, si ses pièces sont toujours disponibles. Sinon, les pièces manquantes sont remplacées.

## 7. Assemblage des photos portées (mode silhouette)
La personne se photographie **en portant** ses vêtements, debout de face, toujours au même endroit, devant un fond vert, appareil fixe, bras le long du corps, en ne changeant qu'une pièce à la fois (les hauts avec le même bas, les bas avec un haut court). Le miroir **assemble** une tenue : le haut d'une photo, le bas d'une autre. Rien n'est généré : tout est photographié. Pas d'essayage virtuel génératif. Le protocole de prise de vue et les commandes : [photos-silhouette.md](photos-silhouette.md) et `scripts/assemblage/README.md`.

**Préparation (sur le PC, `scripts/assemblage/`, Python 3.13 : Pillow, NumPy, OpenCV, torch, transformers et FASHN Human Parser, installés par uv aux versions de `uv.lock`)** — elle ne sert qu'à fabriquer le paquet d'import ; l'app ne dépend pas du PC. Une seule commande (`fabriquer.py`, lancée par `fabriquer.bat` ou `fabriquer.sh`), relancée, fait l'étape suivante.
- **Préparation des photos** : `.jpg`, `.jpeg`, `.png` (toute casse), `.heic` / `.heif` si l'option est installée ; orientation EXIF appliquée ; clé tirée du nom du fichier (sans accents, autres caractères → `-`, 64 au plus). Arrêt sur une photo en paysage, de moins de 1600 px de haut ou sans visage ; avertissements de cadrage (rapport 3:4, hauteur et écart des yeux, centrage, pieds).
- **Détourage par incrustation** : le fond vert devient transparent selon la part de vert indépendante de la luminosité (les ombres du fond partent aussi), on garde la silhouette (plus grande zone au centre) et on retire le reflet vert des bords. Gratuit, sans service externe. Un vêtement vert devient transparent.
- **Repères** : milieu des yeux (détecteur de visage YuNet d'OpenCV, modèle local dans `scripts/assemblage/modeles/`) et milieu de la silhouette entière tous les 10 px sous les yeux (centres robustes). L'échelle reste 1 : l'appareil est fixe et la distance entre les yeux varie surtout avec la rotation de la tête.
- **Lignes**, en px sous les yeux, **calculées** à partir des classes du parseur (`mesures.py`) : `topLow` (point le plus bas de tous les vêtements du haut, veste ouverte comprise ; manches exclues), `bottomHigh` (point le plus haut du bord supérieur du bas). Corrigeables photo par photo dans `corrections.csv`, avec `--regles` pour les voir sur une règle graduée. `onePiece` vaut vrai quand une robe est sur la photo ; `tucked` (haut rentré dans le bas) vient de la colonne `rentre` de `catalogue.csv`.
- **Parseur local obligatoire** : les classes du corps (bras, mains, haut, bijoux…) viennent de FASHN Human Parser, téléchargé une fois par l'installeur (`INSTALLER_PHOTOS.bat` ou `installer_photos.sh`) dans `scripts/assemblage/modeles/`, puis chargé hors ligne parce qu'il est sur le disque : aucune photo ne quitte le PC. Un seul passage par photo, gardé en cache dans le dossier de travail avec l'empreinte de la photo. Sans le parseur, la préparation s'arrête (aucun repli). Sa licence ne permet qu'un usage de recherche ou d'évaluation (THIRD_PARTY_NOTICES.md).
- **Manches** : pour un haut ou une veste à manches, les manches sous l'ourlet sont extraites dans une image à part (pixels classés « haut » sous l'ourlet, sur la carte du parseur déjà en cache).
- **Bras pliés** (par photo, `bras.py`) : couche *bras* (bras, mains, bracelets et manches sous l'ourlet seuls), couche *corps* (photo détourée sans les bras ; le corps caché sous le bras est complété : bord du corps estimé, au plus 30 px sous le bras là où il touche le corps, couleur du corps sûr le plus proche sur la même ligne), couche *manches* (manches sous l'ourlet) ; dans le manifeste, les bords des bras et des manches de chaque côté toutes les 5 lignes, le poignet et le bas de manche, et la boîte de chaque couche (rognée, 1 px transparent autour).
- **Contrôle** : le paquet est revérifié avec les règles de l'import de l'app, et des planches (`controle/tenues-*.jpg`) montrent chaque pièce telle que le miroir la dessine.
- Le paquet (§3.2) contient les photos d'origine, les photos détourées (WebP), les manches, les couches des bras pliés et `manifest.json`, dans un seul zip.

**Rendu (dans le navigateur, `lib/assembly/` + canvas)** pour une tenue :
- source du haut : la veste si la tenue en a une (photo de préférence fermée), sinon le haut ; une robe est affichée seule, telle quelle. Chaussures et accessoires ne sont pas dessinés.
- ligne de coupe `s` (px sous les yeux de la photo du haut, marge `ASSEMBLY_MARGIN` = 6) :
  - haut rentré : `s = max(haut.bottomHigh, bas.topLow) + marge` ;
  - haut plus long que la zone mesurée (`topLow` null) : `s` = 866 ;
  - haut long porté seul, rien que les jambes sous l'ourlet (`bottomHigh` null, t-shirt long) : `s = max(haut.topLow − 2 × fondu, bas.topLow + marge + fondu)`, pour que le fondu reste dans le vêtement (sinon le haut des cuisses de la photo du haut apparaît sous l'ourlet) ;
  - sinon `s = max(haut.topLow, bas.topLow) + marge` ; si `s` dépasse la ceinture de la photo du haut (`bottomHigh`), la bande de ventre entre `topLow + marge` et `bottomHigh − 3` est **étirée** verticalement jusqu'à `s`, si l'étirement reste ≤ 3 ; sinon `s` est ramenée à `bottomHigh`.
- alignement du bas sur le haut : `dy` = différence des yeux, `dx` = différence des milieux de silhouette à la ligne `min(500, s)` (interpolés). Fondu de 10 px de part et d'autre de la coupe. Les manches du haut sont dessinées par-dessus, sous la coupe.
- **Bras pliés** (validés sur un jeu de photos réel) : couper à l'horizontale prenait les bras de deux photos, avec une marche à la coupe. Quand les deux photos ont des données de bras, sous la coupe les bras viennent de la photo du bas, décalés horizontalement ligne par ligne pour rejoindre exactement ceux du haut à la jonction (la coupe, ou le début de la bande de ventre quand elle est étirée) ; le décalage décroît en cosinus jusqu'au poignet du bas (pli de 120 à 250 px) et la main reste à sa place. Le corps sans bras du bas est posé dessous ; sous la fin du pli, la photo du bas reprend telle quelle. Haut à manches sous la coupe (manches longues) : les bras du bas glissent sous les manches du haut, à leur largeur, la main figée à partir de 40 px au-dessus du bas de manche, puis les manches du haut par-dessus. Le plan de dessin se calcule à partir du seul manifeste (`scripts/assemblage/bras_plan.py` est la référence, `lib/assembly` doit donner le même) ; il n'utilise que drawImage (bandes d'une ligne à bords de destination entiers), des fondus en dégradé et la composition source-over, et se dessine toujours à l'échelle 1 (une vignette est réduite ensuite).
- **Rendu sans bras pliés**, à l'identique de la version 1, quand une des deux photos n'a pas de données de bras (paquet sans champ `arms`, photos des tests), pour un haut plus long que la zone mesurée (coupe 866), pour un haut long (coupe ≥ 680, ou poignet du bas au-dessus de la jonction : les mains sont à la coupe), s'il n'y a aucun bras à plier, ou si une précondition du dessin n'est pas tenue (une bande lirait l'autre côté, fondu du corps trop court). Un repli « bras du haut » pour les hauts longs (bras complets de la photo du haut sur le corps sans bras du bas) a été essayé et écarté : mains bien meilleures, mais sur près d'un tiers des tenues concernées le corps complété du bas apparaît en bloc plat sur le côté, sans seuil pour les reconnaître.
- La silhouette est placée à l'écran par les yeux de la photo du haut, sur fond noir. Vêtements foncés (§12) : léger éclaircissement de l'image entière, jamais de halo.
- Limites connues : un bas photographié avec un haut rentré ou une veste à manches laisse voir ce haut à la ceinture ou ces manches ; il faut alors le reprendre en photo avec un haut court. Les réglages sont en px absolus, calés sur un cadrage (photo ramenée à 1600 px de haut, yeux vers 24 % de la hauteur) : une photo cadrée autrement donne des coupes fausses, d'où les avertissements de la préparation.
- Le TypeScript doit rester identique au Python : `scripts/assemblage/ref_fixture.py` écrit des valeurs de référence (données seulement) que les tests de `lib/assembly` relisent dans `lib/assembly/fixtures/*.json`. Ces fixtures, tirées de vraies photos, ne sont pas dans le dépôt : sans elles, les tests qui les lisent sont sautés.

## 7 bis. Fluidité (exigence)
Ce qu'on voit dans le miroir ne doit jamais attendre le réseau.
- **Préchargement** : au réveil de l'écran, à 4 h et après 18 h, la tablette prépare l'assemblage de la tenue à afficher et de ses voisines avant de l'afficher, puis charge en arrière-plan les photos détourées de toutes les pièces propres que le miroir dessine (ni chaussures ni accessoires), avec les couches des bras pliés que ses assemblages dessinent (bas : bras et corps ; haut ou veste : manches de la photo, et corps seulement si, avec l'un des bas, sa bande de ventre est étirée, bras nus), les plus proches de la tenue affichée d'abord, quelques-unes à la fois. Après chaque changement, elle prépare en arrière-plan les assemblages voisins (haut et bas suivants et précédents, veste suivante) ; elle garde une douzaine d'assemblages récents en mémoire, plus ceux que prépare une lecture en cours. Les URL signées changent à chaque lecture : les images sont rangées par URL, pour qu'une photo remplacée au même chemin (nouvel import) ne reste jamais affichée. Changer de pièce n'attend pas le réseau ; un assemblage pas encore prêt se dessine en un instant, et l'assemblage précédent reste affiché en attendant (§4). Les voisines préparées sont celles à un geste (ou une touche). Toutes les 30 s, la tablette lit aussi une empreinte de ses données (GET /api/miroir/touches : pièces propres avec des repères légers de leur assemblage, tenue prévue du jour visé, ville et heure du soir, calculée par le serveur) et le nombre de refus ; si l'empreinte a changé, ou s'il y a moins de refus (seul le téléphone en efface), elle relit les données : un changement fait sur le téléphone arrive sur le miroir en 30 s au plus. Ses propres choix (« oui », « non », « Recommencer ») ne la font pas relire. Un import rejoué qui ne change que les images, aux mêmes repères, arrive à la relecture suivante (réveil après 10 min, 18 h, minuit, 4 h). L'enregistrement part ensuite en arrière-plan, avec une file d'attente s'il n'y a pas de réseau.
- **Gestes** : analysés sur la tablette (MediaPipe avec le GPU, CPU en secours, §5). Pas d'aller-retour réseau entre un geste et l'écran ; l'analyse part juste après le dessin de l'image d'écran, et seuls l'anneau et le debug se redessinent à chaque image de la caméra.
- **Cible** : moins de 100 ms entre un geste ou une touche validés et le changement à l'écran. Animations à 60 images/s, sans saccade quand la caméra passe de 5 à 30 images/s.
- **Tout ce qui est lent** (détourage, fiche Claude, titres) se fait à l'avance ou depuis le téléphone, jamais pendant qu'on est devant le miroir.
- **Pas de dépendance au PC** : l'app ne s'appuie sur aucun ordinateur de la maison. Vercel et Supabase tournent en continu et fournissent le HTTPS qu'exige la caméra.

## 8. Mode kiosque sur la tablette
Ce qui est dans le code, et ce qui se règle dans Android ([tablette.md](tablette.md)).

**Dans le code**
- Préchargement du matin à 4 h (nouvelles URL signées, météo relue) et relectures à 18 h et à minuit (§7 bis) ; la page elle-même n'est rechargée que par l'écran de secours ci-dessous.
- **Écran de secours** : si un écran plante, le miroir reste noir, avec une seule ligne grise « Souci d'affichage, nouvel essai dans un instant », et la page se recharge seule au bout de 30 s, puis de 2 min, puis toutes les 10 min (le compte repart de zéro dès qu'une tenue s'affiche) ; n'importe quelle touche, ou le retour du réseau, recharge tout de suite. L'écran de secours ne tient pas la caméra (seul l'écran du miroir la tient, §5) : la présence ne le réveille pas. Jamais sans réponse du serveur : la page d'erreur du navigateur s'allumerait derrière la vitre. Après 2 min sans touche, la veille revient comme sur les autres écrans de problème (§4 : l'heure seule, fuseau de l'appareil) ; les rechargements continuent, et un rechargement fait pendant la veille repart en veille. La touche ou le toucher qui réveille réaffiche la ligne, sans rien faire d'autre.
- **Sans Wi-Fi** : la page déjà ouverte garde ses tenues et ses images en mémoire et le signale discrètement (« · hors ligne », §4) ; les choix partent plus tard par la file d'envoi. Si minuit passe sans relecture réussie, la tablette recalcule le jour elle-même : le matin, l'en-tête ne dit plus « Demain » et « oui » compte pour aujourd'hui. L'app redemande des URL signées (1 h) à chaque chargement des tenues.

**Pas encore dans le code** (à ne pas promettre)
- Pas d'application installable (PWA), pas de service worker : rien n'est gardé hors ligne après un rechargement de la page.
- L'écran n'est pas gardé allumé par l'app sur le miroir (le Screen Wake Lock ne sert que pendant un import) : la mise en veille de l'écran se règle dans Android.

**À régler sur la tablette**, puisque personne ne peut toucher l'écran derrière la vitre :
- mise en veille de l'écran sur la durée maximale, ou l'option développeur « Rester activé » pendant la charge ; luminosité au maximum, réglée à la main (le navigateur ne peut pas la régler), luminosité adaptative coupée ;
- verrouillage de l'écran sur « Aucun » ;
- caméra autorisée **« Autoriser »**, pas « Uniquement cette fois » : sinon l'autorisation expire et personne ne peut la redonner derrière la vitre ;
- **après un redémarrage ou une coupure de courant, l'app doit revenir seule** : il faut un lanceur au démarrage. Proposé, gratuit, non éprouvé avec cette version : Termux:Boot, qui rouvre l'adresse dans Chrome au démarrage (`am start -a android.intent.action.VIEW -d <URL>`) ; il faut autoriser Termux à « Afficher par-dessus les autres applis ». Solution de secours : Fully Kiosk Browser (lancement au démarrage, rechargement à la reconnexion, écran toujours allumé gratuits ; **l'accès à la caméra par un site web est une fonction payante**, indispensable aux gestes).

## 11. Choix de conception
1. **Essayage virtuel génératif** (§7) : écarté au profit de l'assemblage des photos portées. Plus de budget d'essayage.
2. **Navigateur kiosque** (§8) : Chrome et les réglages d'Android ; pour le retour après redémarrage, Termux:Boot (gratuit) ou Fully Kiosk Browser (caméra payante).
3. **Styles** (§3) : une liste par pièce plutôt qu'une seule valeur.
4. **Refus** (§6) : ce que montre la silhouette, pas la tenue complète.
5. **Détourage** : incrustation sur fond vert, gratuite, pour les photos portées (§7) ; pour une photo à plat, un PNG déjà détouré (gratuit) ou Bria sur fal.ai (payant).
6. **Prise de photo des vêtements** : portée, sur fond vert, même endroit et même pose pour le mode silhouette (§7) ; à plat pour le mode simple.
7. **Commande du miroir** : pas de manette ; les gestes des bras (méthode des zones, gestes tenus), le clavier en secours (§5).
8. **Occasion du jour** (décontracté, habillé, sport) : pas encore tranché. Les styles des pièces sont enregistrés mais ne filtrent rien.
9. **Préparer demain** : gardé (§3, §4, §6).

## 12. Retours d'expérience
- **Vêtements foncés** : en couleurs réelles, un jean brut ou un pull marine disparaissent derrière le miroir sans tain. Il faut les éclaircir ou leur donner un contour clair.
- **Fond des images** : une photo rectangulaire allume tout son rectangle. Seuls les détourages et les fonds noirs passent.
- **Gestes** : directions vues de la personne face au miroir ; conflit entre main ouverte et glissement (d'où la méthode des zones : la main s'arme devant la poitrine, et le réveil se fait par la présence, sans geste) ; immobilité pour les maintiens ; pause après chaque geste ; un écran de debug sur la tablette est indispensable pour régler les seuils derrière la vitre.
- **Devant un miroir, on se tourne souvent** pour se voir de profil, et de profil les épaules se confondent dans l'image (d'où la garde « de profil », §5) ; le premier appel de chaque modèle bloque la page plus d'une seconde (d'où le préchauffage). Reste à mesurer sur la tablette, avec la vraie caméra et `?gestures=debug`, sans rien changer aux seuils d'ici là : le |u| des armements (certains passent entre 0,7 et 0,8, au bord de `CENTER_IN`), « bas suivant » (à vérifier, avec le risque de « se recoiffer » au-dessus de la tête), « bas précédent » (la main n'atteint la ligne du bas qu'à 1 ou 2 cm près, et un bras qui retombe devant soi peut le donner), et les scores du Gesture Recognizer sur des mains qui ne font pas de geste (un pouce reconnu à 0,69–0,71 sur une main qui ne fait pas de geste a rempli l'anneau à 70 %).
- **Sans tactile** : prévoir le retour après redémarrage (verrouillage sur « Aucun », lancement au démarrage) et une autorisation caméra permanente.
- **Luminosité** : le navigateur ne peut pas la régler, il faut la mettre au maximum à la main.
- **Chaleur** : la caméra et l'analyse tournent en permanence. Prévoir de l'air derrière la tablette et vérifier au bout de quelques heures.
- **Touches** : ne jamais supposer les codes d'un clavier inhabituel. Un écran de test et de mapping (`?touches=test`), puis des tests ; mais ne jamais bloquer l'écran dessus.

## 13. Hors périmètre
Pas de multi-utilisateur, pas de boutique en ligne, pas de réseau social, pas d'app native, pas de reconnaissance faciale (le détecteur de visage du §7 ne sert qu'à aligner les photos, sur le PC), pas d'essayage virtuel génératif.
